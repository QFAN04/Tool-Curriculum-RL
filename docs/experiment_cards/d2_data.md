- 日期：2026-11-13（本地完成，未用 GPU）
- 代码：`src/tcrl/data/build.py`、`src/tcrl/data/split.py`、`src/tcrl/tool_env.py`、`src/tcrl/reward.py`

- 原始数据：`Agent-Ark/Toucan-1.5M` 的 `SFT` config，3 个 parquet，119,287 行，Apache-2.0（放在 `data/raw/`，不进 git）
- 产物：`data/processed/all.jsonl`、`data/processed/splits/*.jsonl`（不进 git，可由脚本重建）；`data/manifests/splits.json`（进 git，含每个 split 的 id 哈希与留出族列表）

## Toucan SFT 子集的构成（实测）
| subset | 行数 |
|---|---|
| irrelevant（工具不相关，不该调用） | 40,000 |
| multi-turn | 35,243 |
| single-turn-original | 28,254 |
| single-turn-diversify | 15,790 |

它是多步的 agent 轨迹，不是现成的单轮函数调用数据。我们只取「一个用户轮次 + 一轮工具调用（可并行多个）」的样本，标准答案是这一轮的全部调用。

## 构建时的筛选（`build.py`）
| 原因 | 行数 |
|---|---|
| 多个用户轮次 | 33,378 |
| 不是恰好一轮工具调用 | 11,774 |
| 提示过长（工具定义 + 问题 > 12,000 字符） | 5,720 |
| **参数值在问题里找不到依据** | 15,415 |
| 标准调用自身不符合 schema | 39 |
| 解析失败 | 2 |
| **保留：调用样本** | **14,875** |
| 保留：拒绝样本 | 38,084 |

「有据」过滤是这一步最重要的决定：奖励是完全匹配，所以只留下每个参数值都能在问题里原样找到的样本（枚举值和布尔值除外）。像「为这个场景写一段图片描述」这类参数没有唯一答案，留着只会让奖励变成噪声。代价是丢掉约一半单轮样本，并且数据偏向「从问题里抄参数」的题，不覆盖需要推理或改写才能得到参数的情况——这是本项目任务范围的一个明确限制。

另外两处清洗：问题里的 HTML 注释（Toucan 改写时留下的备注）被去掉；拒绝样本的目标回复只取原回复的第一段、最多 600 字符（原回复中位数约 1,150 字符）。

## 工具族与划分（`split.py`，seed 20261113）
- 族的定义：**参数名集合相同的工具算一族**（无参数的工具按函数名）。共 370 族。
- 试过并放弃：按工具共现做连通分量，结果约九成样本并成一族（很多样本同时带多个 server 的工具）。
- 留出族的样本进 `*_unseen`；训练侧的样本连**可见工具列表**里都不含留出族；部分沾到留出族的 3283 条丢弃。
- 训练侧每族最多 300 条（封顶前 9343 条），避免天气、词典这类工具主导。
- 拒绝样本按 15% 配比加入每个 split。

| split | 总数 | 调用 | 拒绝 | 标准调用涉及的族数 | 多调用样本 | 标准调用在训练集中原样出现 |
|---|---|---|---|---|---|---|
| test_unseen | 1924 | 1635 | 289 | 46 | 346 | — |
| dev_unseen | 547 | 465 | 82 | 11 | 23 | — |
| test_seen | 1176 | 1000 | 176 | 96 | 153 | 284 |
| dev_seen | 588 | 500 | 88 | 74 | 69 | 186 |
| sft | 2187 | 1859 | 328 | 128 | 317 | — |
| rl | 2188 | 1860 | 328 | 126 | 348 | — |

`*_seen` 最后一列把「见过的族」再分成两块：标准调用在训练集里原样出现过的（问法不同，相当于改写）和没出现过的（新的参数组合）。

sft + rl 的调用样本里：无参数调用约 18%，多调用约 18%。

## 已知局限
1. 族的定义偏粗（按参数名），「未见族」里可能有功能相近但参数名不同的工具，比如另一套命名的天气工具。它保证的是「这组参数的工具没见过」，不保证「这类功能没见过」。
2. 任务被限定为参数可从问题直接抄到的单轮调用，难度偏低；D3 的 probe 会告诉我们 SFT 之后还剩多少可学空间。
3. Toucan 的轨迹是模型生成的，标准调用不保证最优。人工核查见下。

## 人工核查（Go/No-Go ②）

### 第 1 轮：用户核查（`docs/notes/d2_audit_100_v1_user.md`，修复前的数据）
用户判定：对 65 / 错 3 / 存疑 32。主控按「给定问题与工具，调用集合是否正确且唯一」的任务标准归类这 35 条：
- 确有问题约 15–20 条：自由文本参数截取范围不唯一 6；关键词不唯一 3；可选参数填不填都行 1；工具选择或调用数量可疑 4；拒绝样本其实有工具可用 1–2；另有大小写不一致（标准答案写 `tokyo`，问题里是 `Tokyo`）。
- 两数运算的操作数可互换 6 条：标准答案都按问题中出现的顺序填，视为可学的约定，保留，记为局限。
- 约 13 条是怀疑「工具返回的结果能否完全满足需求」，超出本任务的判定标准（原因之一是核查表把工具说明截断到了 200 字符，核查说明也没讲清这一点）。
- 按任务标准，正确率约 80–85%，**未达 95%**。

### 据此做的修改
1. 超过 5 个词的字符串参数必须在问题里被引号原样括起来（`build.py: grounded`）。
2. 可选参数的枚举值、布尔值也必须能在问题里找到；必填的不要求。
3. 带通用执行 / 搜索类工具的拒绝样本丢弃。
4. 奖励比较字符串值时不区分大小写，并统一排版连字符与引号（`tool_env.py: _norm_value`）。函数名与参数名仍区分大小写。

修改后的数据量（取代上文各表中的数字）：调用样本 13,846，拒绝样本 23,668；sft 2318、rl 2318、dev_seen 588、test_seen 1176、dev_unseen 541、test_unseen 1842。以 `data/manifests/splits.json` 为准。单测 38 项通过。

### 第 2 轮：子 agent 标注（`docs/notes/d2_audit_100_v2.md` / `_v2_agent.md`，修复后重新抽样，seed 8）
- 标注标准写明了：只判调用集合是否正确且唯一；不因怀疑工具输出是否够用而扣分；两数运算按出现顺序填算对。
- 结果：OK 93 / WRONG 1 / AMBIGUOUS 6（调用 78 / 1 / 6，拒绝 15 / 0 / 0）。另有约 5 条它标了 OK 但自己注明拿不准。
- 残留问题的类型：参数格式无法从题面推出；多步请求只覆盖了一部分；无参数天气工具被用来回答指定地点的问题；改写后的问题与工具只是大致对应。这些规则过滤抓不到。
- **这是模型标注，不是人工核查，且仍低于 95%。** 第 2 轮抽样之后又加了第 4 条里的排版字符归一化（针对它发现的一条）。

### 结论（待用户决定）
按原定的 ≥ 95% 标准，Go/No-Go ② 目前不算通过。残留噪声估计在 5–10%，属于规则抓不到的类型。
