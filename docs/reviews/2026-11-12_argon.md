### 逐条审查（C1–C9）

**C1 LoRA 下的 SDPO 老师：部分正确**
- **理由**：源码诊断准确（`zip(parameters())` 在单侧挂 LoRA 时会因参数数量与形状不匹配直接报错或错位）。但主控倾向的「先 (a) 后 (b)」并非最优：(a) 固定老师会让自蒸馏退化为向初始 SFT 模型的静态上下文蒸馏，学生分布漂移后老师无法同步进化；(b) 对 `lora_A/B` 分别做 EMA 存在双线性交叉项误差（$\text{EMA}(BA) \neq \text{EMA}(B)\text{EMA}(A)$）。(c) `TrustRegionTeacher` 在 LoRA 下**直接可用**（在 logits 层面对 `ref` 和带 adapter 的 `student` 做插值，完全绕开参数级 `zip`），唯一代价是老师端多一次前向且无历史时间平滑。
- **修改建议**：冒烟直接用 **(c)**（零改代码且有动态老师）；若显存/耗时受限再写 **(b)**（老师同挂 LoRA，按参数名匹配 `lora_` 键做小步长 EMA）。

**C2 SDPO 后期崩溃：部分正确**
- **理由**：换 JS 散度对症，但「限制 150–200 步 + 选 ckpt」只是掩盖后期崩溃，而非排雷。工具调用崩溃最常见的主因是**全对组（acc=1.0）未过滤导致熵坍缩**，以及 **top-k 截断蒸馏在 JSON 结构 token 上的尾部概率失配**。
- **修改建议**：① 剔除组内全对样本（或对其跳过蒸馏更新）；② 监控策略熵与 KL，调小老师 EMA 速率（如 $\le 0.005$）。

**C3 小模型记忆 vs 泛化：部分正确**
- **理由**：仅看「未见工具族」会把「记住旧工具」和「4B 零样本迁移能力不足」混在一起；若两算法在未见工具族都涨不动，将无法下结论。
- **修改建议**：评测拆为 **2×2 矩阵**（已见工具族的新参数组合 vs 未见工具族），并同时报告 `pass@1` 与 `pass@8`（若 `pass@1` 涨而 `pass@8` 不涨/跌，说明只是分布锐化而非学会新技能）。

**C4 反馈含标准答案：有问题**
- **理由**：含答案的 SDPO 是在**学生 on-policy 错误轨迹**上用带答案的老师分布做 token 级逆向/JS 蒸馏（消除曝光偏差），不同于离线 SFT。但拿「有答案 token 级监督的 SDPO」直接对比「仅有 0/1 标量奖励的 GRPO」属于**信息量不对称的不公平对比**。
- **修改建议**：主表必须包含**「仅给执行/校验报错、不含标准答案」的 SDPO** 与 GRPO 公平对决；「含标准答案 SDPO」应定义为 Oracle 引导上限，或补一个**在失败样本上对标准答案做在线 RFT/SFT** 的基线。

**C5 二值奖励：部分正确**
- **理由**：修正多调用 dict 合并 bug 非常关键。但二值奖励会产生**算法偏向**：当难题组内全错（acc=0）时，GRPO 优势全为 0（零梯度），而含反馈的 SDPO 依然能从错误反馈中获得稠密梯度！
- **修改建议**：训练前先跑 step-0 探针统计「混合组比例」（$0<\text{acc}<1$）；若比例过低（$<25\%$），必须对两者统一引入格式/工具名/参数三级奖励，否则 GRPO 被系统性压制。

**C6 自生成伪标签过滤：部分正确**
- **理由**：「先写调用 $y^*$ 再写问题 $x$」天然自带伪标签。若按盲投票高一致性过滤，确实会筛掉模型不会的难题，背离「失败驱动」。
- **修改建议**：用 $k=8$ 次采样**与预设标准调用 $y^*$ 的匹配率 $p_{\text{pass}}$** 做**带通滤波**：剔除 $p_{\text{pass}}=0$（题目歧义/废题）和 $p_{\text{pass}}>0.8$（已掌握简单题），只保留 $p_{\text{pass}} \in [0.1, 0.7]$ 的边界样本。

**C7 出题失败率：有问题**
- **理由**：`Qwen3-4B-Base` 仅做「答题 SFT」后，指令遵循局限在输出工具调用，直接做逆向「看错题出自然语言题目」极易崩坏（胡乱输出 JSON 或复读）。
- **修改建议**：在**公共 SFT 阶段**混入 5%～10% 的「给定 Schema + 标准调用 → 生成用户问题」逆向样本。由于 S/U/F 三臂共享同一个 SFT 起点，完全不破坏三臂对照公平性。

**C8 等成本三臂对照：有问题**
- **理由**：「训练步数相同」与「生成过滤 GPU 时间计入总成本」**自相矛盾**（U/F 多花了大把采样过滤时间，若步数还和 S 一样，总成本就不相等）。
- **修改建议**：固定三臂的 **RL 训练步数与新引入样本条数相同**（对比数据质量），同时增设一个 **S+（用省下的合成 GPU 时间多跑训练步数的静态臂）** 以对齐总算力成本；确保 U 与 F 唯一变量是采样分布（均匀 vs 失败加权）。

**C9 SFT → RL 衔接：部分正确**
- **理由**：Merge 后重挂 LoRA 路线可行，但有三个实操坑。
- **修改建议**：① 合并时必须先转 `fp32` 计算 $W + \frac{\alpha}{r}BA$ 再转回 `bf16`，防低精度截断；② SFT 严禁过拟合（控制在 1–2 epoch），防止进入 RL 时策略熵过低导致采样完全重复；③ RL 阶段 LoRA 需挂全线性层（`all-linear`）。

### 最可能导致项目失败的前三个问题与未预见风险
1. **Base 模型充当 SDPO 老师与出题器的能力不足（头号风险）**：4B-Base 仅经窄域答题 SFT，缺乏通用阅读理解与反事实纠错能力，很可能看不懂报错反馈、也出不出合格题目（建议验证是否改用 `Qwen3-4B` Instruct/Post-trained 作基座，或在 SFT 混入带反馈修正与出题数据）。
2. **GRPO 与 SDPO 的信噪比/信息量严重不对等**：全错组（acc=0）上 GRPO 零梯度而 SDPO 有标准答案引导，实验结论极易变成「有标签蒸馏打赢无梯度 RL」的伪结论。
3. **14 天工期被两轮自生成流水线冲垮**：逆向出题、$k$ 次采样校验、每轮人工抽检 100 条加两轮三臂 RL，工程链路过长；建议先跑通**单轮课程（Round 1）**确认收益，再决定是否跑 Round 2。
4. **未想到的风险（工具族泄漏与格式坍缩）**：按工具族隔离评测时，自生成阶段若在 Prompt 里给模型看全局工具库，可能把测试集近义工具模式泄漏进合成数据；另外 SDPO 只对 top-k logits 蒸馏时，未归一化的余项处理不当会导致生成的 JSON 闭合括号丢失。
